# 聊天记录统一入库

把微X、QX、钉X 三个桌面端的本地聊天记录解密后，合并成一个统一的本地 SQLite 库，
作为 Hermes 个人记忆的数据源（下游见[个人记忆库](/ai-app/memory-vault)）。
全程只读本机自己账号的数据，**不退出客户端、不走第三方服务、数据不出本机**。

## 为什么走本地解密

- 官方开放接口要么不提供个人聊天记录，要么要组织管理员在开放平台开权限，个人无法自助开通。
- 社区现成的导出工具随时可能下架。
- 三个客户端的本地库都是**加密的 SQLite**（SQLCipher 或自定义的页级加密），
  解密后就是普通 SQLite，可以直接用 SQL 增量读取。

密钥的获取方式各平台不同（复用已有导出工具保存的密钥、客户端运行时获取、由本地配置推导），
这里不展开具体方法。原则是：**密钥只存本机，不进仓库、不进日志、不进笔记**。

## 统一库结构

```
各平台加密库 ──解密──▶ 明文副本 ──增量抽取──▶ unified.db
                                              messages(platform, conversation, sender,
                                                       create_time, content_type, content ...)
```

- 一张 `messages` 表，用 `platform` 列区分来源，下游不用关心消息来自哪个客户端。
- 只有纯文本类型进入下游提取；图片、文件、卡片只保留类型标记。
- 联系人显示名**优先用备注名**，其次才是昵称——备注是自己起的，比昵称好认也更稳定。
- 噪音群、已退的群写进屏蔽清单，刷新时自动排除。

## 增量刷新

- **按分片文件的 mtime 跳过没变的分片**，再只取 `create_time` 大于上次水位的新消息。
  没有新消息时一次刷新约 0.3 秒。
- 另备一个全量重建脚本：先清空该平台的记录再全量导入，天然去重，用于修复。

## 坑：只解主库会漏掉运行期的新消息

SQLite 开了 WAL 模式时，客户端运行期间的新消息先写进 `-wal` 文件，要到 checkpoint 才合并进主库。
**只解主库，客户端开着的这段时间的消息全都看不到。**

做法：把 WAL 按帧解密，重算每帧的 checksum，再和主库一起打开。

判断「WAL 要不要重解」时踩过一个坑：一开始拿「上次运行时间」和 WAL 的 mtime 比，
但上次运行时间记的是批处理**开始**时刻，往往晚于 WAL 的实际写入时间，
于是被误判为「没变化」，消息一直停在中午，实际晚上还有。
改为记录 WAL 的 **mtime + size 签名**，签名一变就重解。

> 教训：判断文件有没有变，用文件自身的签名比较，不要拿「我上次什么时候看过」去比。

## 其他小坑

- 有的库带自定义 FTS 分词器，直接 `PRAGMA quick_check` 会报 `no such tokenizer`，
  只读业务表时绕开 FTS 虚表即可。
- 目录名只是哈希，真实账号 ID 要从客户端日志里找。
- 客户端升级可能换加密版本或配置字段，刷新失败时先查配置变化，不要先怀疑脚本。
