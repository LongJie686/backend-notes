# 创意对话

[创意生图](/projects/production/creative-imagegen)的对话版：用户用大白话跟模型来回聊，
模型决定是新生成一张图还是在上一张基础上改，后台出图。和创意生图共用生图渠道与提示词人设，
独立 pm2 进程。

## 每轮对话怎么跑

```
组装上下文（会话记忆 + 长期记忆 + 团队经验 + 热榜精简版）
  → 对话 LLM 输出 JSON 动作：chat / generate / edit
  → generate：写 brief → 后台按岗位人设优化提示词 → 出图
  → edit：直接写英文改图指令，以基准图为参考出图
```

- **回复先返回，图片随后刷新**：提示词优化和出图都在后台，本轮请求不等，页面先放图片占位。
- **历史里的助手消息按当时输出的 JSON 回放**，保持模型每轮都输出 JSON 的格式惯性。
- **当前基准图和本轮上传图作为多模态输入**附在本轮用户消息里，模型看得到正在改的图。

## 公平排队：不限流、不拒绝，只排队

- 总并发 N 个 worker，**每个用户同时最多 k 个**，超出的在自己的队列里排，用户之间轮流取。
  一个人一次提交再多也占不满全部名额，别人照样能插进来。
- 同一会话一次只处理一轮（按会话加锁），按用户加信号量。
- 页面显示「排队中」，而不是报错让用户重试。

## 三层记忆

| 层 | 内容 | 关键做法 |
|----|------|---------|
| 会话记忆 | 最近 N 轮原文 + 更早轮次的结构化浓缩 | 增量补丁折叠 |
| 个人长期记忆 | 用户偏好、禁忌、习惯做法 | 提取必须带证据 |
| 团队经验 | 多人共有的做法 + 同事蒸馏材料 | 管理员审核才生效 |

### 会话记忆：不做「摘要的摘要」

借鉴 Letta 的「块 + 溢出折叠」，但不照搬它的摘要方式——每次把旧摘要连同新消息重新摘要，
越叠越失真，而且折叠时直接丢图。这里让模型对结构化记忆**输出增量补丁**（加/删条目），
程序校验后合并；图片以「图#N：说明」保留脉络。
**只有补丁成功落库后，被折叠的轮次才移出上下文**——折叠失败不丢信息，下一轮再试。
组装时再按 token 预算兜底裁掉最旧轮次。

### 个人长期记忆：借鉴 mem0，补回更新与删除

- 把该用户已有记忆（**用序号代替真实 id，防模型编造**）+ 新对话一起给模型，
  让它输出 新增 / 更新 / 删除 操作。mem0 新版只增不改，这里加回来：偏好变了就覆盖、被推翻就删。
- **每条新增必须带证据**（出自哪几条消息），没有证据的丢弃。
- 不存一次性要求和临时尝试（借鉴 Open WebUI 的记忆审查提示词）。
- 触发点：换会话、用户说「记住」、每天定时。

### 团队经验：一个人跑偏不能影响所有人

候选来自两处：同一岗位下 ≥ M 个不同用户都出现的偏好（模型聚类，**人数由程序核对，不信模型报的数**），
以及同事上传的经验材料。审核通过后按岗位注入所有人的对话；被驳回过的不会再冒出来。

## 参考图编号失配（一次线上复盘）

用户反馈「老照着上一轮出图」。查线上历史统计发现两个缺陷：

1. **编号失配**：对话模型按全会话编号写「#27」，生图模型只收到按位置排的几张图，不知道哪张是 #27。
   会话第一轮编号恰好等于位置所以总是对的，往后越来越错——统计中半数以上的 #N 对不上实际附图。
2. **基准图强塞**：编辑时无条件把上一轮成图排第一。「图1背景换成图2背景」这类请求，
   用户说的图1/图2 是本轮上传，基准图是多出来的一张还排最前，模型就照着上一轮出图。

修复：提示词里的编号**按本组实际附图顺序逐个换成「reference image K」**，开头加一行图序说明兜底；
基准图只在没上传、或对话明确点名时才带；存库的是换算后的提示词，重试原样复用。

教训：**两个模型之间传引用，不能各自用各自的编号体系**，必须在交接处做一次显式换算。

## 渠道调用的几个坑

- **通道级故障立即换下一家，不在同通道重试**：HTTP 错误、超时，以及「HTTP 200 但正文是
  `{"code":500}`」都算通道故障。旧判据把后者当「模型回了空内容」同通道再试，每轮白等几分钟。
  只有「通道正常但输出不合格」（不是 JSON、被截断）才同通道再试一次。
- **有的模型不理会 `response_format=json_object`**，仍然把 JSON 包在 ```` ```json ```` 代码块里。
  干脆不发该参数，靠指令 + 本地剥壳解析。
- **流式只为测首 token 时间**，结果仍等完整后再解析。SSE 响应头常不带 charset，
  `requests` 会按 ISO-8859-1 解码出乱码，**流式正文必须按字节自己解 UTF-8**。

## 运维细节

- **在途计数要对账**：`safe_restart` 靠账本里的 active 判断能否重启，但账本会失真——
  进程崩溃后残留旧值，或其他 import 了同模块的脚本把线上 active 清零。
  做法：启动时把 0 落盘；进程内维护真实在途数，定期对账，失真最多存在一个周期。
- **热榜注入控制 token**：趋势数据整份约 5.6 万字，每轮只带精简版（约 2600 token），
  对话里提到的条目再展开详情；文件按 mtime 缓存，更新后下一轮自动生效，过期不带。
- **告警只推需要人处理的故障**（记忆提取整体失败、通道鉴权失效），同类告警有冷却期，上线重启不推。
- 删除的会话保留 30 天后彻底清理；上传残留临时文件 1 天后清理。
