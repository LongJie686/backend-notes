# 办公与辅助机

除了跑在[线上服务器](/projects/production/)的生产工作流，日常还有两台机器承担常驻任务。
三台机器按「谁该对外、谁该常驻、谁拿得到数据」分工：

| 机器 | 定位 | 承担什么 |
|------|------|---------|
| [办公电脑](/projects/infra/office-pc) | 开发 + 依赖本机数据的任务 | 开发调试、需要浏览器登录态的采集任务 |
| [辅助电脑](/projects/infra/aux-pc) | 局域网内常驻服务 | 自建模型网关、钉钉 AI 助手、字幕高亮等内部工具 |
| 线上服务器 | 对外公网入口 | 生产工作流 + 统一门户，见[生产工作流](/projects/production/) |

## 机器之间怎么连

```
                 线上服务器（公网入口，nginx + 门户鉴权）
                  ▲ 反向 SSH 隧道（-R），云上只监听回环
                  │
办公电脑 ──正向 SSH 隧道(-L)──▶ 辅助电脑（无公网 IP）
本地回环端口                   内部服务
```

- **组网走 Tailscale**：辅助电脑没有公网 IP，机器之间的 SSH 都走 Tailscale；
  同一局域网时会自动打洞直连。
- **内部服务对外靠反向隧道**：辅助电脑主动连线上服务器，把端口映射到云上的回环地址，
  再由 nginx 反代 + 门户统一鉴权。云上这些端口不直接暴露，鉴权也只在门户做一处。
- **办公电脑用内部服务靠正向隧道**：客户端只认 `127.0.0.1:<端口>`，
  由一个守护脚本维持 `-L` 隧道转到辅助电脑。服务换机器时只改隧道目标，客户端配置不动。

## 服务迁移的经验

把常驻服务从办公电脑迁到辅助电脑时，几条通用做法：

1. **每个服务独立 venv**，共享一份基础 Python，互不影响。
2. **开机自启用计划任务**（开机触发 + 定时检查、实例已在则跳过），不依赖有人登录。
3. **切换前做双空闲确认**：间隔十几秒两次确认无进行中的请求，再停旧进程；
   数据文件逐个比对 hash 一致后才以新机为准，旧数据保留作回退。
4. **端口和消费者不变**：迁移只换隧道目标，使用方无感。
5. **依赖本机独有数据的不迁**：浏览器登录态、本机会话数据这类东西，
   迁过去要么拿不到，要么得把凭据复制到公共机器上，得不偿失。
